# Package INPUT, PADS, TEXT AND MENUS: 64-bit rva -> 32-bit VA

Written by the research agent for this package. Work in progress: see "Status" at the end for what is still open.
Conventions: 32-bit addresses are VAs (image base 0x400000, rva = VA - 0x400000). "lc" = local client number.
Tools used: Ghidra 32 and 64 projects (own copies), `image32.bin` bytes, the 64-bit exe on disk. Everything below is *observed* in decompiles/bytes unless the line says "concluded".

## 1. Keyboard / key events

### Key event (CL_KeyEvent) - 64-bit rva 0xd0f80, native.c line 3009 (`key_event_hook`) and `pad_key` line 2242
- 32-bit: VA 0x4d2350 (rva 0xd2350), convention: cdecl (caller does `ADD ESP,0x10`, plain `ret`), arguments: `(int lc, int key, int down, unsigned time)` - same order as 64.
- **hook site (call in the event loop)**: the loop is VA 0x43a300 (64: 0x1fbb80); the call is at VA 0x43a339 (rva 0x3a339), `e8 12 80 09 00`, args pushed `time(edi), down(ebx), key(edx), 0`. It is the only direct caller of 0x4d2350.
- bytes at VA 0x4d2350: 8b 4c 24 0c 53 8b 5c 24 08 55 8b eb 69 ed 28 0d
- bytes at VA 0x43a339: e8 12 80 09 00 83 c4 10 eb c3 52 6a 00 e8 95 62
- evidence: both decompiles have the same tree: key slot update (down count / repeat count), the `devgui` strcmp (32: string 0x6b40b0), key 0x60 / 0x7e / 0x1b tests, key 200 and `< 0x80` -> ESC substitution when `(catchers==0 && connstate in 1,2,>3)`, the ESC branch (32: calls 0x454820 for a menu, 0x4fab00 for a playing state 1..2, 0x410f70(lc,2) otherwise), the menu branch (32: 0x454820 = UI key handler = 64's 0x24c540), and the `+binding` -> `"%s %i %i\n"` branch.
- **Important difference**: 64 binds a key to an *action index* (int at key slot +0, run through `0xce450`), 32 binds a key to a *command string* (pointer at key slot +8, `"+attack <key> <time>\n"` through `0x4ff300` -> `Cbuf_AddText(lc, text)`, and `-binding` through `0x410580`). There is no action index in 32. See section 2 for how pads do it in 32.
- key table offsets (observed): 32: per lc block at `0x8893b8 + lc*0xd28` (rva 0x4893b8): `+0` count of keys down, then 256 slots from `+4` of `{int down, int repeats, char *binding}` (0xc bytes): down `0x8893bc + lc*0xd28 + key*0xc`, repeats `0x8893c0 ...`, binding string pointer `0x8893c4 ...`. 64: per lc stride 0x1930 from rva 0x5300e0 (count), slots `{int action index @0x5300f0, ... char *binding @0x5300f8}` of 0x18 bytes. (Default binding for ESC (key 27) in 32: pointer to "togglemenu" at VA 0x889508.)
- confidence: verified (both decompiles compared)

### Key catchers - 64-bit rva 0x533cb0 (per lc stride 0x10), native.c lines 2322, 2637, 2845, 3012
- 32-bit: VA 0x925bb8 (rva 0x525bb8), per lc stride 0x10 (`param_1*0x10`), a uint of flags: bit 0x1 console, 0x8 (key-capturing/"no binding"), 0x10 UI/menu, 0x20 (chat/other). The int at +8 (VA 0x925bc0 + lc*0x10... see note) is the connection / UI state used in the ESC branch (`iVar6 = (&DAT_00925bc0)[lc*4]` : in 64 `(&DAT_140533cb8)[lc*4]`).
- evidence: 0x4d2350 reads `(&DAT_00925bb8)[lc*0x10]` with the same `& 0x21`, `& 0x10`, `& 1`, `& 8` tests as 64 reads `0x533cb0`. Written by the 32 function 0x4a33b0 (64's 0xd1c10 "set key catchers" - concluded from the single WRITE xref and the call pattern; not decompiled).
- confidence: verified for the address, likely for who writes it.

### View angle accumulators - 64-bit rva 0x533d14 pitch / 0x533d18 yaw (native.c 2116, 2122, 2669, 3193...)
- 32-bit: pitch VA 0x925c34 (rva 0x525c34), yaw VA 0x925c38 (rva 0x525c38), floats in degrees. **Per local client stride is 0xbe9c in 32 (0xce9c in 64)**: `0x925c34 + lc*0xbe9c`.
- relation (observed, both builds identical): they sit at +0x54 / +0x58 of the *mouse state* (64: 0x533cc0, 32: 0x925be0 + lc*0xbe9c), together with +0x48 / +0x4c (the smoothing speeds `DAT_00925c28 / 0x925c2c`, 64: 0x533d08 / d0c) and +0x44 (a multiplier read by the mouse read function).
- evidence: 32 FUN_00578fe0 (the mouse-look, 64: 0xcfcf0): `_DAT_00925c38 = _DAT_00925c38 - x*m_yaw` (yaw), `_DAT_00925c34 += m_pitch * y` (pitch), the same expressions as 64's `DAT_140533d18 -= ...` and `DAT_140533d14 += ...`; the cl block per-lc stride is visible in FUN_00579a80 (`unaff_EBX * 0xbe9c`).
- confidence: verified (code compared); the context-swap range the 64 code uses (`{0x533cb8, 0x68}`) is another package's job: mouse state begins at least at 0x925be0 in 32.

### Mouse read - 64-bit rva 0xcf4b0, call sites 0xcfd23 (in 0xcfcf0) and 0xd0061 (in 0xcff70), native.c line 2986
- 32-bit: function VA 0x578f10 (rva 0x178f10), **register convention (usercall)**: `ESI = mouse state*` (per lc: `0x925be0 + lc*0xbe9c`), stack args `(float *x, float *y)` pushed right-to-left `push y; push x` (caller does `ADD ESP,8`), plain `ret`; ESI preserved by the callee; result through the two pointers. (64: `rcx = state, rdx = x, r8 = y`.) A hook has to be a naked stub that reads ESI. All callers are the two sites, so hooking the function entry covers both hooks:
  - call site 1: VA 0x579000 in FUN_00578fe0 (64: 0xcfcf0 mouse-look, state fixed 0x925be0 = lc 0 only; `MOV ESI,0x925be0` right before the call at 0x578ffb), bytes `e8 0b ff ff ff 83 c4 08`.
  - call site 2: VA 0x5799e8 in FUN_00579960 (64: 0xcff70; EAX = lc, EDI = usercmd*, `ESI = lc*0xbe9c + 0x925be0` computed at 0x57996e/0x57997c), bytes `e8 23 f5 ff ff 8b 0d d8`.
- bytes at VA 0x578f10: 83 ec 0c 8d 4c 24 08 8d 54 24 04 8b c6 e8 7e ff
- other callee notes: 0x578ea0 (usercall EAX = state) reads the raw deltas (m_filter 0x925bd8: smoothing).
- evidence: decompile 0x578f10 matches 64 0xcf4b0 (cl_mouseAccel, sensitivity, `*(state+0x44)`, `sqrt(x*x+y*y)/frametime`, the two outputs `fVar3*x`, `fVar3*y`); the dvars sit in the register function 0x4f3480 (cl_mouseAccel -> VA 0x925bb0, sensitivity 0x8941d4, m_pitch 0x8941dc, m_yaw 0x8941d8, cl_freelook 0x931a7c, m_filter 0x925bd8).
- the matcher guess 0x526720 for 64's 0xd03a0 is wrong (it is a different, unrelated function: material/model loop).
- confidence: verified.

### usercmd maker - 64-bit rva 0xd03a0 (called at 0xcf8b1), native.c 3026 `make_cmd_hook`
- 32-bit: VA 0x579a80 (rva 0x179a80), *likely* (not fully compared): `_memset(EAX, 0, 0x40)` first (EAX = out usercmd, 0x40 bytes), then reads the cl block with stride 0xbe9c, calls the kbutton-flags function 0x578bd0 (ECX = EDI = cmd), mouse look 0x578fe0, the controller path 0x579960. ## 2. Pad actions: names -> kbuttons (what `pad_action` / `pad_binding` / `pad_action("weapnext")` become)

### Action table and executor - 64-bit rva 0x3be770 (0x4c names), 0xd1810 name -> index, 0xce450(lc, index, key) (native.c 2217-2239, control.c 172-200)
- **32-bit: no counterpart for the table and the executor.** The key code of 32 stores a command string per key and the buttons are ordinary console commands (`+attack`, `-attack`, ...). The 32 build already uses this in `control.c bind_f` (`game_cbuf_addtext("+activate 511\n")`).
- What exists instead (observed):
  - command registrations (static `cmd_function_t`, `{next, name, 0, 0, function, flags=1}`, 0x18 bytes) at VA 0x888b..0x889240; the 4-byte `Cmd_AddCommand` calls for the dynamic ones sit in the register function around VA 0x4f03a8-0x4f0b00 (`CALL 0x428090(name, function, struct, flag)`).
  - **kbutton handlers**: `+attack` = VA 0x5786c0: `push esi; mov esi,0x888ac8; call 0x578340; pop esi; ret`; `-attack` = VA 0x5786d0 same with `0x5783e0`. So `0x578340` is "key down" and `0x5783e0` "key up", both **usercall with ESI = kbutton***, **no stack args**: they read the key number and time from the *current command's argument vector* (`Cmd_Argv(1)` = key, `Cmd_Argv(2)` = time through the globals `0x144c950` (nesting index), `0x144c994[]` (argc), `0x144c9b4[]` (argv)); with no argument the key is -1.
  - kbutton_t layout and the *input block layout are identical to 64*: kbutton = `{int key[2]; int downtime; int msec; byte active; byte wasPressed}` = 0x14 bytes; block per lc stride 0x21c both builds; block base 32 = VA 0x8889b0 (rva 0x4889b0), 64 = rva 0x52fbc0. Offsets in the block (same in both): +attack 0x118, +melee 0x168, +frag 0x140, +smoke 0x154, +breath_sprint/+holdbreath 0x12c, +usereload 0x1a4, +gostand 0xf0, +activate 0x17c, +reload 0x190, +prone 0x1b8, +sprint 0x1f4, +moveleft 0x78, +moveright 0x8c, +lookup 0x50, +lookdown 0x64, +strafe 0xa0, +speed 0xb4 ... (see the table in "kbutton table" below). Verified by reading the ESI constants of the 32 handlers against the 64 `0xce450` switch.
  - the key-down / key-up bodies (64: `0xd0620(kbutton, key, time)` and `0xd06f0`) are inline in 0x578340 / 0x5783e0 in 32; the logic is the same (observed): down: if key == key[0] or key[1] -> nothing; first free slot takes the key; if !active { downtime = time; active = wasPressed = 1 }; up: clear the slot with that key, if both slots are empty { active = 0; msec += time - downtime (or `+ frametime/2` when time == 0) }.
- **Recommended 32 form of `pad_action`** (concluded, not run): do not go through the command line: write the same few lines on the kbutton in the live context's input block (address `0x8889b0 + lc*0x21c + offset`, no hooks needed), or push `"+attack 511 <time>\n"` through `game_cbuf_addtext` as `control.c` already does (the Cbuf is executed in the frame loop, so it runs in whatever context is live then - not controllable, hence the first form).
- confidence: verified for the layout, the handlers and the key-down / key-up semantics.

#### kbutton table (observed, 64 `0xce450` case -> block offset; the 32 handler's ESI constant minus 0x8889b0 is the same offset)
+attack 0x118, +melee 0x168, +frag 0x140, +smoke 0x154, +breath_sprint 0x12c (also +holdbreath 0x12c), +usereload 0x1a4, +gostand 0xf0, +moveleft 0x78, +moveright 0x8c, +lookup 0x50, +lookdown 0x64, +strafe 0xa0, +activate 0x17c, +reload 0x190, +prone 0x1b8, +sprint 0x1f4, +speed_throw: kbutton 0xb4 AND +toggleads_throw kbutton 0x1e0 (64 `case 0xd` runs both; 32 handlers: +speed_throw VA 0x578910 / -speed_throw 0x578930 push 0x888a64, +throw VA 0x5788d0, +toggleads_throw VA 0x5788f0 / -toggleads_throw 0x5788e0 - **not yet decompiled, see open items**).

#### Names the pads use that are *not* kbuttons in 64 either (`0xce450` cases) and where they are in 32
- `+actionslot N` / `-actionslot N` (d-pad): 64 `0xc0a30(lc, N-1)` / `0xca490`. 32: commands `+actionslot` (handler VA 0x45f3c0) and `-actionslot` (VA 0x407100), registered at 0x4f0423 / 0x4f0439; the slot number is `Cmd_Argv(1)` (binding string `"+actionslot 1"` + key + time makes argv = `+actionslot 1 <key> <time>`: *unknown*: whether the key/time are argv 2/3). Not decompiled.
- `weapnext` / `weapprev`: 32 handlers VA 0x430b60 / 0x44f840 (cmd registrations 0x4f03de, 0x4f03fc). 64 `0xc2d90(lc, 1|0)`.
- `+scores` / `-scores`: 32 handlers VA 0x55dac0 / 0x55da90 (0x4f03b7, 0x4f03cd). 64 `0x932b0` / `0x932d0`.
- `pause`: 32 command struct VA 0x931d3c, handler VA 0x57a4c0 (64: index 65 = `0xd45d0`).
- **`togglemenu`** (Start in play): in 64 `0xce450` has **no case for index 63** (`togglemenu`): it only sends `"n 63"` to the server (the client command of `notifyOnPlayerCommand`, `0xd21a0`, format string rva 0x3308cc). So Start in play works through a script, or not at all (**unverified; check this in the 64-bit build: if nothing in the mod's scripts waits for "togglemenu" the Start button does nothing in play**). In 32 `togglemenu` is only the default binding string of the ESC key slot (key 27, `0x889508` is its binding pointer, text at 0x1589d24); ESC itself is special-cased in 0x4d2350 (pause menu: `0x4fab00(lc)` / `0x410f70(lc,2)`). So the 32 Start = `key_event(lc, 27, 1/0, time)` (same function as `pad_key`), which opens the pause menu the way the keyboard does.
- `centerview` struct VA 0x889270 (handler 0x4e9940). Not used by pads.
- confidence: verified for the existence and addresses, unknown for the argument conventions of actionslot / weapnext.


### Key numbers for menu keys (`pad_menu`, `lobby_pad_thread`, `mw2coop_menukey`) - 64-bit key name table rva 0x3bdb70
- 32-bit: the same numbers: TAB 9, ENTER 13, ESCAPE 27, SPACE 32, UPARROW 154, DOWNARROW 155, LEFTARROW 156, RIGHTARROW 157. Name table VA 0x72f688 (rva 0x32f688), entries `{char *name, int key}` of 8 bytes (TAB at 0x72f688, ENTER 0x72f690, ESCAPE 0x72f698, SPACE 0x72f6a0, UPARROW 0x72f6b0 ...).
- confidence: verified (read from the image).

### Pad Start / Back in play and `notifyOnPlayerCommand`
- 64 sends `"n <action index>"` to the server for every action through `0xce450` (via `0xd21a0`, format string rva 0x3308cc `"n %i"`); the game's scripts use `notifyOnPlayerCommand` on that.
- 32 does the same one level up: **`Cmd_ExecuteSingleCommand` VA 0x4da360 (rva 0xda360), cdecl `(int lc, int source, const char *text)`**, bytes `8b 4c 24 0c b8 00 02 00 00 2b 05 d8 9e 45 01 56`. It tokenizes `text` (0x600050), then calls `0x4a2950(lc)` which sends `"n <index>"` (format string at VA 0x6d3a38 `"n %i"`, `"nt %s"` for unknown names; the index from 0x43ed70(name); test 0x44b6e0) and then walks the command list (head VA 0x144c9d8) and calls the handler. The Cbuf executor calls it at VA 0x600285 (`push text; push source(edx); push lc(ebx); call`).
- **Consequence for the port (concluded)**: a pad press that must reach the scripts (`+actionslot N`, `+smoke`, `+frag`, `+melee`, `weapnext` ... all `notifyOnPlayerCommand` candidates) should be run as a command line through `0x4da360(0, source, "+actionslot 1 511 <time>")` on the main thread in the live context, not by flipping the kbutton: the kbutton write misses the `n <index>` message. The `source` value: `unknown` (the Cbuf passes what it was given; take the one 0x600285 passes for a console command, needs a test).
- confidence: verified for the chain; the `source` argument and the 511 key convention are unknown for this path (control.c bind_f already sends `"<name> 511\n"` through `Cbuf_AddText`, which reaches the same function).

## 3. Text and names (HUD)

### Game message window draw - 64-bit rva 0xcb4f0, native.c line 3368 `msgwin_hook`
- 32-bit: VA 0x4713b0 (rva 0x713b0), size 175, convention: cdecl (plain `ret` at 0x47145e, the caller cleans), 12 stack arguments `(int lc, int window, int x, int y, int horz, int vert, void *font, float scale, <arg9>, int arg10, int arg11, int arg12)`. The 32 version is a thin wrapper that calls the window text routine `0x577df0(&windows[lc][window], x, y, round(scale * const), horz, vert, arg10, 1.0f, arg12, arg11)`; the 64 `how` argument (param_12 chooses 0xcbaf0 or 0xcbdb0) has no switch in 32. lc, window, x, y keep their positions (1st to 4th), so the test `window == 2 && ctx == 0` etc. works on the same arguments.
- bytes at VA: a1 c0 a7 86 00 83 ec 10 83 78 10 00 0f 85 99 00 (the 64 hook compares 20 bytes; use these 16)
- window indices (observed): the window names table at VA 0x730148: `0 "gamenotify obituary"`, `1 "boldgame"`, `2 "subtitle"`: the same meaning as in 64 (window 2 = subtitle, window 0 = obituary / game notify).
- window array: 32 base VA 0x885f80 (rva 0x485f80), per lc stride 0x4858 bytes (0x1216 dwords), per window 0x34 bytes (0xd dwords): `&windows[lc][window] = 0x885f80 + lc*0x4858 + window*0x34`. (64's decompile shows `0x52f348 + (lc*0x9c + window)*8`: another shape; the context-swap ranges of the context package must use the 32 numbers, not a translation.)
- evidence: the `cg_drawpaused` string (VA 0x6c8e08) is read in both with the same test (`cl_paused && cg_drawpaused`); the dvar `cl_paused` global is VA 0x86a7c0 (64 DAT_1413260e8 by the same test).
- confidence: verified (shape, strings, window names); the window struct layout beyond the stride is unknown.

### Names over the other players: the loop - 64-bit rva 0x93ac0 (loop at 0x93d90), `name_self_install` native.c line 3382
- 32-bit: the loop is its own function **VA 0x55ea00 (rva 0x15ea00), `(int lc)` on the stack (cdecl)**, bytes `83 ec 28 56 8b 74 24 30 56 e8 02 f2 f8 ff 83 c4`. The per-client entity array whose bit 1 at `+0x164` is tested: starts at VA 0x792864 - 0x1c... stride 0x198 (64: 0x441090, 0x1a8); the loop ends at 0x792b94 (2 clients).
- confidence: verified (decompiles compared, bytes read). The patch stub has to be rewritten for x86 (the jump targets are 5-byte `jmp`).

## 4. Pad pictures in texts (padglyphs.c)

### Binding text function - 64-bit rva 0xd0e40 `(lc, command, out[2][0x80])` returns the count (0 = unbound -> "KEY_UNBOUND")
- 32-bit: **VA 0x475680 (rva 0x75680), cdecl `(int lc, const char *command, char *out)`, plain `ret`**: a wrapper `mov eax,[esp+4]; mov ecx,[esp+8]; push edi; mov edi,[esp+0x10]; push eax; call 0x579e80; add esp,4; pop edi; ret`. The real function 0x579e80 is usercall (ECX = command, EDI = out, stack: lc), returns 0..2, writes the key names with 0x4aa830, "KEY_UNBOUND" when none; 0x579c70 (EAX = lc, stack: command, &int[2]) searches the 256 key slots (64: 0xd1880). bytes at VA 0x475680: 8b 44 24 04 8b 4c 24 08 57 8b 7c 24 10 50 e8 ed.
- callers (observed): the text localizer **0x6235e0** (64: 0x2513b0, call at 0x2513ce) calls it at **VA 0x6235f6** (`e8 85 20 e5 ff`); the script builtin `getkeybinding` (builtin table entry at VA 0x731e24: `{name 0x69dc3c, function 0x5d51e0, 0}`; Ghidra has no function there, the code starts at 0x5d51e0) calls it at **VA 0x5d51f6** (`e8 85 04 ea ff`) with lc 0 (64: 0x1913fa in 0x1913e0). ### Text draw and its call - 64-bit rva 0x433b0, called at 0x44c12 from the render command handler 0x44b20 (text in rcx)
- 32-bit: the render command table is at VA 0x71b19c (23 handlers, rva 0x31b19c; 64: rva 0x3705b8), index 15 = the text command = **handler VA 0x5390f0** (cdecl, one argument: the pointer to the command pointer; a command begins `{u16 type, u16 size}`, type 0x10 for text, written by `R_AddCmdDrawText` VA 0x50e310). - bytes at VA 0x537ec0: 55 8b ec 83 e4 f8 81 ec 8c 00 00 00 8b 45 28 53 (the hook is on the call site, not on the function)
- **inline picture format (observed in 0x537ec0 / 0x5377d0)**: `'^'`, then a code byte `1` (or `2`), a width byte, a height byte, then a **4-byte** `Material *`; the draw skips the code byte, w, h and the pointer as `local_70 += 7`. 64: `'^',1,w,h` + 8-byte pointer. - size formula (0x5377d0, observed): `((n - 16) * fontHeight + 16) / 32` times the text scale for width and height: the same as 64.
- confidence: verified (decompile of the handler and of the draw loop); the pointer position inside the 7 bytes is concluded (7 - 3), the material read itself was not followed.
